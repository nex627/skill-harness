# 对话收尾 — 通用 C+A 引擎

## 定位

**Workflow Harness 的对话级通用门控层。**

各业务 skill 负责自己的 P（计划）和 D（执行），本 skill 统一提供：
- **C 阶段引擎**：按各 skill 定义的验收清单逐项核验，不通过则阻断，支持降级完成
- **A 阶段引擎**：按沉淀规则写入 wiki / 知识库 / 原始记录，确保经验闭环

> 像发货前核对装箱单一样，不交付完不算完成；像出门前检查钥匙手机一样，不沉淀完不让走。

## 与 Skill Harness 的关系

```
Skill Harness 完整体系（重型业务场景）
  P 计划 → D 执行 → C 检查 → A 沉淀
                       ↑         ↑
                       │         │
        对话收尾 skill = 通用 C 引擎 + 通用 A 引擎
```

| 层级 | 完整 Workflow Harness | 对话收尾（本 skill） |
|------|----------------------|---------------------|
| P 计划 | 双源信息采集 + 方案规划 | 各 skill 自行负责 |
| D 执行 | 分段落地 + 结构化产出 | 各 skill 自行负责 |
| C 检查 | AI自检 + 人工复核 + 阻断机制 | **统一提供引擎**，按各 skill 的验收清单核验 |
| A 沉淀 | L3入库 + L2提炼 + 版本管理 | **统一提供引擎**，写入 wiki/short-term/raw |

**核心原则：各 skill 定义"什么算完成"，本 skill 负责"检查是否真的完成"。**

## 触发规则

| 触发词/场景 | 说明 |
|------------|------|
| 对话结束、再见、拜拜、晚安 | 激活记忆门控（A 阶段） |
| 多步骤任务报告"完成"前 | 激活交付核验（C 阶段） |
| 任务启动时判断级别 | 自动分级：轻量/中量/重型 |

## 三级任务分级机制

| 级别 | 适用场景 | 门控内容 | 示例 |
|------|---------|---------|------|
| **一级·轻量** | 简单对话、问答、闲聊 | 仅记忆沉淀（A 轻量版） | "这个概念什么意思" |
| **二级·中量** | 多步骤任务、有明确产出物 | 交付核验（C）+ 记忆沉淀（A） | 晨报、文档蒸馏、简单开发 |
| **三级·重型** | 标准化业务场景、高价值产出 | 完整 Workflow Harness PDCA | 内容运营、产品设计、大型项目 |

### 分级判断规则

```
1. 是否有明确产出物？→ 无 = 一级
2. 产出物是否≥2个且有依赖关系？→ 否 = 二级
3. 是否属于标准化业务场景且有历史沉淀？→ 是 = 三级
```

## C 阶段引擎：交付核验（二级及以上）

### 验收清单定义方式（各 skill 自行维护）

每个需要交付门控的 skill，必须在自身文档中定义：

```yaml
交付验收清单:
  产物列表:
    - 名称: [产物1]
      路径: [文件路径模板]
      验证方式: 文件存在 / 结构合规 / 内容可读 / 命令执行通过
      结构约束: [如"8个section"、"标题含日期"]
      关键级别: 关键 / 非关键
  完成定义: 所有关键产物全部通过验证
```

### C 阶段执行流程

```
步骤1：加载对应 skill 的验收清单
步骤2：逐项核验
  - 文件存在性检查
  - 结构合规检查
  - 内容可读性检查
步骤3：结果判定
  - 全部关键项通过 → C_DONE → 进入 A 阶段
  - 有关键项缺失 → C_BLOCKED → 继续执行缺失项
  - 非关键项失败 → 降级完成，记录降级范围
步骤4：输出核验报告
```

### 阻断与降级规则

| 核验结果 | 状态 | 处理方式 |
|---------|------|---------|
| 全部通过 | `C_DONE` | 进入 A 阶段 |
| 关键项缺失 | `C_BLOCKED` | **继续执行缺失项**，不得宣称完成 |
| 关键输入失败 | `C_BLOCKED` | 停止执行，向用户报告阻塞项 |
| 非关键项失败 | `C_DOWNGRADED` | 进入 A 阶段，标注降级范围 |

## A 阶段引擎：记忆沉淀（所有级别）

### 三层沉淀结构

| 层级 | 写入位置 | 内容 | 触发条件 |
|------|---------|------|---------|
| L1 | `memory/raw/YYYY-MM-DD.md` | 情绪状态、重点产出路径 | 有情绪/重点产出时 |
| L2 | `wiki/对应知识库.md` | 战略决策、工作进度、产品需求、重要认知 | 结论达到 wiki 级重要度时 |
| L3 | `memory/short-term.md` | wiki-derived 条目，关联检测与新鲜度追踪 | 有 wiki 写入时自动同步 |

> 注：这里的 L1/L2/L3 是对话级沉淀的三层，与完整 Harness 的三层知识库（L1公共/L2行业/L3私有）是不同维度。

### 记忆门控检查清单

```
- [ ] 扫描本次对话/任务，是否有需要写入 wiki 的结论？
  - 战略决策 → 战略记录
  - 工作进度 → 工作进度
  - 产品需求 → 需求记录
  - 投资相关 → 投资追踪
  - 重要认知 → 认知/方向/感知知识库
- [ ] 如果有 wiki 写入 → 是否已更新 short-term？
- [ ] 是否有情绪/重点产出需要补充到 raw/？
```

## 执行顺序（强制执行）

```
任务启动
  ↓
判断级别
  ├─ 一级（轻量）→ ──────────────────────→ A 阶段（记忆沉淀轻量版）
  ├─ 二级（中量）→ D 阶段由 skill 执行 → C 阶段（交付核验）→ A 阶段（记忆沉淀）
  └─ 三级（重型）→ 完整 Workflow Harness PDCA（C 和 A 由本引擎驱动）
```

**关键规则：C 阶段未通过，不得进入 A 阶段。任务没做完，记忆就不完整。**

## 为什么独立成 skill？

| 没有本 skill | 有本 skill |
|-------------|-----------|
| 收尾检查埋在元系统几百行里，AI"忘了" | 门控器独立存在，触发条件明确 |
| "知道要检查"但"到时没检查" | 不检查完不让走，强制执行 |
| 每个 skill 各自实现验收，标准不统一 | 统一 C+A 引擎，各 skill 只需定义验收清单 |
| 依赖 AI 自觉 | 依赖机制，不依赖自觉 |
| 多步骤任务只做一半就报告完成 | 交付清单逐项核验，缺项不得宣称完成 |

## 设计约束

1. **只检查不判断** — 本 skill 是门控器，不做业务决策
2. **统一引擎** — C 和 A 的执行逻辑只有一份，各 skill 共享
3. **可扩展** — 新增 skill 只需定义验收清单，不需重写检查逻辑
4. **三级渐进** — 不强制所有任务都走重型流程，按需升级

## 禁忌

- 禁止跳过交付核验直接宣称任务完成
- 禁止交付门控未通过就进入记忆沉淀
- 禁止本 skill 越权做业务决策
- 禁止每个 skill 重复实现 C/A 逻辑
