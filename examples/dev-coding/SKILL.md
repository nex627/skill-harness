# Vibe Coding

## 定位

**AI 辅助开发的工程约束型流水线 skill。**

从需求到部署全流程管控，每次开发自动复用历史架构经验，上线后自动沉淀 bug 和优化记录。

## 触发规则

| 触发词 | 说明 |
|--------|------|
| 写代码、开发功能、加功能 | 启动完整 PDCA 流程 |
| 技术选型、架构设计 | 仅启动 P 阶段 |
| debug、修 bug | 跳过 P 阶段，直接 D 阶段 |
| 代码评审、code review | 仅启动 C 阶段 |

## 三层知识库

| 层级 | 路径 | 内容 |
|------|------|------|
| L1 公共库 | `L1/dev-ops.md` | 通用工程规范、设计模式、安全基线 |
| L2 行业库 | `L2/{tech-stack}/` | 技术栈最佳实践、开源方案、兼容规则 |
| L3 私有库 | `L3/{project}/history.md` | 历史 bug、架构踩坑、迭代经验 |

## PDCA 执行流程

### P 阶段 — 需求分析与技术方案

| 顺序 | 动作 | 阈值 |
|:---:|------|------|
| 1 | 读取 L3 历史 bug + 架构踩坑 | ≥3条 |
| 2 | 搜索同类开源方案 + 技术选型对标 | ≥3个 |
| 3 | 整合技术方案（需求 × 历史教训 × 社区方案） | 完整覆盖 |

**标准产出**：

| 编号 | 名称 | 要求 |
|------|------|------|
| P0 | 技术调研报告 | 历史踩坑 + 开源方案对比，≥800字 |
| P1 | 需求规格 | 用户故事（≥5个）+ 验收标准 |
| P2 | 技术方案 | 架构设计 + 模块划分 + 技术选型 + 风险预判 |

**阻断规则**：
- 历史 bug < 3条 → 标记首次，放行
- 对标 < 3个 → 阻断
- 需求不清晰 → 阻断

---

### D 阶段 — 编码实现

三段式产出：

**D1 执行摘要**（≥300字）

包含：架构决策、技术选型理由、核心模块说明、与方案的一致性。

**D2 详细交付物**

| 模块 | 要求 |
|------|------|
| 完整代码 | 含注释，符合规范，可运行 |
| 架构说明 | 模块划分 + 依赖关系 + 数据流 |
| 接口文档 | 请求/响应示例（如有 API） |
| 测试用例 | ≥5个，覆盖正常 + 边界 + 异常 |
| README | 快速启动指南 + 配置说明 |

**D3 偏差记录**（≥100字）

记录与 P 阶段技术方案的偏差、编码中的调整。

---

### C 阶段 — 代码校验

**AI 自检评分表**：

| 维度 | 检查内容 | 权重 |
|------|---------|:---:|
| 语法正确 | 无语法错误、import 完整 | 20% |
| 边界处理 | 空值、异常、并发、超时 | 25% |
| 安全性 | 注入、XSS、密钥泄露 | 25% |
| 可维护性 | 命名、注释、模块化 | 15% |
| 测试覆盖 | 正常 + 边界 + 异常 | 15% |

阈值：综合 ≥ 80 分通过。

**人工复核**：代码审查（自审或团队 review）。

---

### A 阶段 — 上线沉淀

| 步骤 | 产出 |
|:---:|------|
| 1 | 部署验证（功能正常、性能达标） |
| 2 | bug 记录（≥3条，含根因 + 修复方案） → 写入 L3 |
| 3 | 架构优化建议 |
| 4 | 版本号 + 下次迭代建议 |

---

## 多模型适配

| 场景 | 叠加模型 | 说明 |
|------|---------|------|
| 新功能开发 | PDCA + 设计思维 | 用户共情 → 原型 → 验证 |
| Bug 修复 | PDCA（跳过 P） | 直接 D → C → A |
| 重构 | PDCA + DevOps | 编码 → 测试 → 部署 → 线上复盘 |
| 性能优化 | PDCA + DMAIC | 定义 → 测量 → 分析 → 改进 → 控制 |

## 禁忌

- 禁止跳过历史 bug 读取（避免重复踩坑）
- 禁止 AI 一步式输出完整代码（必须先过 P 阶段）
- 禁止代码未经测试直接合并
- 禁止上线后不复盘
