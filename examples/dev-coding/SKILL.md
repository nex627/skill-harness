# 开发项目

## 定位

**开发项目的多步骤流水线 skill。**

把开发工作拆成三步：调研 → 文档 → 编码。每步产出需要人工检查通过才进下一步。执行经验自动沉淀到知识库，下次开发不重复踩坑。

## 触发规则

| 触发词 | 说明 |
|--------|------|
| 开发项目、写代码、做功能 | 启动完整流程 |
| 技术调研、竞品调研 | 仅步骤1 |
| 写需求文档、写开发文档 | 仅步骤2 |

## 知识库

| 层级 | 路径 | 用途 |
|------|------|------|
| L2 行业库 | `L2/dev/best-practices.md` | 技术栈最佳实践 |
| L3 私有库 | `L3/dev-project/history.md` | 历史 bug、架构踩坑 |

---

## P 阶段 — 规划（执行前必做）

**读取历史经验**：
- 读取 L3 历史 bug 和踩坑（≥3条，首次标记放行）
- 读取 L2 技术栈最佳实践
- 读取 L1 通用工程规范（可选）

**产出**：执行方案（步骤清单 + 技术选型 + 风险预判）

---

## D + C 阶段 — 按步执行 + 人工检查

### 步骤1：搜集资料（竞品调研 + 资料搜集）

- **输入**：用户需求描述
- **动作**：
  1. 搜索同类产品/开源项目（≥3个）
  2. 收集技术资料、文档、教程
  3. 整理技术选型方案
  4. 预判技术风险
- **产出**：调研报告（竞品分析 + 技术选型 + 风险预判）

**检查点**（人工检查）：

| 检查项 | 标准 |
|--------|------|
| 竞品覆盖 | ≥3个同类产品/方案 |
| 技术选型 | 有明确建议和理由 |
| 风险预判 | 识别了主要技术风险 |
| 可执行性 | 调研结论能指导下一步 |

> ✅ 全部通过 → 进入步骤2
> ❌ 任一不通过 → 返回步骤1补充，附带修改意见

---

### 步骤2：产出文档（需求文档 + 开发文档）

- **输入**：步骤1的调研报告
- **动作**：
  1. 写需求规格（用户故事 + 验收标准）
  2. 写技术方案（架构 + 模块划分 + 接口设计）
  3. 写开发计划（任务拆解 + 优先级）
- **产出**：需求文档 + 开发文档

**检查点**（人工检查）：

| 检查项 | 标准 |
|--------|------|
| 需求清晰 | 每个需求有验收标准 |
| 技术方案可行 | 架构合理、模块划分清晰 |
| 接口定义完整 | API 请求/响应定义清楚 |
| 可执行 | 拿着文档能直接写代码 |

> ✅ 通过 → 进入步骤3
> ❌ 不通过 → 返回步骤2修改

---

### 步骤3：执行编码

- **输入**：步骤2的需求文档 + 开发文档
- **动作**：
  1. 按文档搭建项目结构
  2. 逐模块编码
  3. 写测试用例（≥5个，覆盖正常+边界+异常）
  4. 自测通过
- **产出**：可运行代码 + 测试用例

**检查点**（人工检查）：

| 检查项 | 标准 |
|--------|------|
| 功能完整 | 覆盖所有需求 |
| 测试通过 | 所有测试用例通过 |
| 代码规范 | 命名、注释、结构符合规范 |
| 边界处理 | 空值、异常、并发已处理 |

> ✅ 通过 → 进入 A 阶段
> ❌ 不通过 → 返回步骤3修改

---

## A 阶段 — 经验沉淀

| 步骤 | 动作 | 产出 |
|:---:|------|------|
| 1 | 系统自动记录执行偏差（实际耗时 vs 预估、异常次数） | 偏差报告 |
| 2 | 收集人工反馈（调研够不够深、文档够不够清晰、哪里卡了） | 反馈清单 |
| 3 | 踩坑记录写入 L3（≥3条，含根因） | 经验入库 |
| 4 | 版本号 + 下次优化建议 | 版本记录 |

---

## 五大设计约束

1. **多步拆解** — 调研→文档→编码，三步不可合并
2. **人工检查点** — 每步通过才进下一步
3. **明确产出** — 调研报告/文档/代码，每步有实物
4. **经验沉淀** — 系统自动 + 人工反馈 → L3 知识库
5. **历史复用** — 执行前读取历史 bug，避免重复踩坑

## 禁忌

- 禁止跳过调研直接写代码
- 禁止跳过文档直接编码
- 禁止跳过检查点
- 禁止编码完成后不复盘
